01

Design tools by risk

Read the fictional ticket and customer history, then tag category and priority automatically. A customer-facing reply is a different action and needs an explicit reviewer decision.

02

Build four in-process MCP tools

Use tool(), Zod schemas and createSdkMcpServer for get_ticket, get_customer_history, set_priority and send_reply. The teaching helpdesk is a local JSON fixture, with no email provider.

03

Pause at the native permission boundary

Leave send_reply out of allowedTools. The real canUseTool callback waits on a browser approval promise while the draft remains unrecorded.

04

Approve, edit or reject

Approve the original draft, edit its body through updatedInput, or reject the native call. The UI cannot retarget a reply to another ticket. Each exact approved ticket/body grant can be consumed once.

05

Handle errors and limits

Return isError for missing tickets and a deliberately unavailable history fixture. Preserve a native one-turn failure and validate a real typed triage result.

06

Audit and batch safely

PostToolUse records actual tool results. Inspect local JSON and approval decisions together. Batch starts one fresh query per ticket and requires a separate review for each reply.
